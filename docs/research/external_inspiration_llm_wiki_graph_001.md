## 1. Purpose

This document summarizes six external inspiration sources reviewed for a future MellyCore feature direction: a static-first, docs-driven visualization of MellyCore's own `shared_context/` and `docs/` knowledge as a node/edge graph. Every source below is treated as **conceptual inspiration only**. No code, markup, assets, or text has been copied from any external project. Where a source has a restrictive license (for example GPL), that fact is stated explicitly and copying is refused.

This is a research and product-direction artifact. It authorizes no implementation.

## 2. Source-by-Source Summary

### 2.1 Karpathy LLM Wiki (persistent Markdown knowledge system)

**What it is (as described/observed conceptually):** A workflow pattern where an LLM agent maintains a persistent Markdown wiki. Raw sources are treated as immutable ground truth; the wiki itself is a derived, editable layer the agent (and a human, via an editor such as Obsidian) can revise. The wiki tracks contradictions between sources rather than silently overwriting one claim with another.

**Core ideas:**
- Raw sources are immutable; derived notes are mutable and versioned.
- The wiki is treated like a codebase: the human is the "IDE operator," the LLM is the "programmer," the wiki is the "code."
- Contradictions between sources are tracked as first-class objects, not silently resolved.
- Schema/instructions for the agent are themselves stored as Markdown files the agent reads before acting.

**What MellyCore should adopt:**
- The immutable-source / derived-note separation. `[[../../shared_context/CONTEXT_GRAPH_SCHEMA]]` formalizes this as `SourceRef` (immutable reference) versus `ContextNode` (derived, versionable).
- Explicit contradiction tracking as a durable ledger, not an ephemeral chat observation. See `[[../../shared_context/CONTRADICTION_LEDGER]]`.
- Agent-readable schema files as the contract for how any agent may extend the graph. See `[[../../shared_context/CONTEXT_GRAPH_SCHEMA]]` and `[[../../shared_context/SOURCE_INGEST_WORKFLOW]]`.

**What MellyCore should avoid for now:**
- Any live agent write-loop that edits the graph autonomously. MellyCore's posture requires human review before publish (see `[[../../shared_context/SOURCE_INGEST_WORKFLOW]]`).
- Obsidian or any specific vault-editor integration — no plugin, no file watcher, no live sync target in this phase.

**Licensing/copying caution:** No file structure, prompt text, or plugin code has been copied. Only the conceptual pattern (immutable source / mutable derived note / contradiction tracking) is referenced.

### 2.2 LLM Wiki Newsroom (AI-generated cross-linked wiki)

**What it is (as described/observed conceptually):** A pattern for generating a cross-linked wiki of entities and concepts from a catalog of sources, with contradiction analysis between sources and a publish/review gate before content goes live.

**Core ideas:**
- Source catalog as the entry point (a list of ingested sources with provenance).
- Entity/concept pages generated from sources, cross-linked to each other.
- Contradiction analysis as a distinct analytical pass, separate from summarization.
- A publish/review gate: generated content is not automatically public.

**What MellyCore should adopt:**
- The source-catalog-first structure: every node in the MellyCore graph must trace back to a `SourceRef` (see schema doc).
- The publish/review gate concept, applied strictly: nothing generated by an ingest pass becomes a committed doc/static fixture without human review (see `[[../../shared_context/SOURCE_INGEST_WORKFLOW]]`, step "human review").
- Contradiction analysis as its own workflow step, feeding the ledger.

**What MellyCore should avoid for now:**
- Any automatic "publish" step. In MellyCore, "publish" means committing a static Markdown/JSON fixture after human review — never an automated live site update.
- Any notion of the graph being "always on" or continuously regenerating; MellyCore's MVP is static and manually refreshed.

**Licensing/copying caution:** No page templates, generation prompts, or UI copied. Only the catalog → entity/concept → contradiction → publish-gate pipeline shape is referenced.

### 2.3 Gitingest (repo-to-context-pack tooling)

**What it is (as described/observed conceptually):** A tool pattern that turns a repository into a single prompt-friendly digest: a file tree, a token count estimate, and concatenated file contents, useful as context for an LLM.

**Core ideas:**
- Repo digest = file tree + token budget + selected file contents.
- File allowlist/blocklist to keep the digest relevant and bounded.
- Read-only operation against the repo; it does not mutate anything.

**What MellyCore should adopt:**
- The shape of a bounded, read-only "context pack": file tree summary, token budget, changed-files summary, and a safety summary layered on top. See `[[../../shared_context/CONTEXT_PACK_GENERATOR_SPEC]]`.
- Explicit allowlist/blocklist thinking, extended in MellyCore to also block secret-shaped paths (`.env`, credential files, local databases) by policy, not just by size.

**What MellyCore should avoid for now:**
- Any private/GitHub token usage. The MellyCore context pack concept is repository-local and read-only; it must never call an authenticated API or use a personal access token.
- Any automatic mutation of files based on the digest. The context pack is an output artifact, not a write path.

**Licensing/copying caution:** No source code, CLI argument names, or output formatting has been copied from any specific gitingest-style tool. Only the general "repo digest for LLM context" concept is referenced.

### 2.4 Homepage (gethomepage-style static dashboard/startpage)

**What it is (as described/observed conceptually):** A self-hosted static dashboard/startpage pattern: a config-driven grid of service cards, a search bar, and optional widgets, organized into groups.

**Core ideas:**
- Config-driven layout: cards and groups are defined in data, not hardcoded per-instance markup.
- Search-first navigation across many cards/entities.
- Bookmarks/widgets as supplementary, non-critical panels.

**What MellyCore should adopt:**
- The config-driven card/group layout idea, applied to the Knowledge Graph Console's sidebar (cluster groups) and node search. See `[[../../docs/product/knowledge_graph_console_spec]]`.
- Search-first interaction as the primary way to find a node, rather than requiring visual graph-scanning alone.

**What MellyCore should avoid for now:**
- Any code, CSS, icon set, or component copied from the gethomepage project or similar GPL-licensed dashboard projects. gethomepage is GPL-3.0-licensed; MellyCore's design system and (eventual) implementation are original work and must not incorporate GPL code. This is a **hard licensing boundary**, not a style preference.
- Service-monitoring specific features (uptime pings, container status, API health widgets) — out of scope; MellyCore is not a service dashboard.

**Licensing/copying caution:** **GPL code copying is explicitly forbidden.** No CSS, component markup, icon assets, or JavaScript from gethomepage or any GPL-licensed dashboard project may be copied into MellyCore at any phase. Only the abstract "config-driven card grid with search" concept is referenced here.

### 2.5 Neon (branchable, storage/compute-separated database platform)

**What it is (as described/observed conceptually):** A database platform whose architecture separates storage from compute and supports instant, branchable snapshots of that storage — "branch a database like you branch git."

**Core ideas:**
- Storage/compute separation as an architectural pattern.
- Branchable snapshots: a full, independent copy of state that can be created, inspected, and discarded cheaply.

**What MellyCore should adopt:**
- The **metaphor only**: a "context snapshot" as a versioned, named, point-in-time export of the graph's static fixture data (e.g., `context-graph-snapshot-2026-07-07.json`), so a reviewer can compare graph state across ingest passes. This is a plain file-based snapshot, not a database feature.
- The storage/compute separation idea as a naming/architecture reference for a *future* phase, if MellyCore ever needs a real backing store — explicitly not now.

**What MellyCore should avoid for now:**
- Any actual database integration, connection string, ORM, or hosted service. No Neon (or any other DB) account, project, branch, or credential is created or referenced by this spec.
- Any implication that the graph has live compute behind it. The MVP is static fixtures checked into the repo.

**Licensing/copying caution:** No SQL, schema DDL, dashboard UI, or product copy has been copied. Only the branch/snapshot metaphor is referenced, applied to flat files.

## 3. What MellyCore Adopts (Summary)

1. Immutable source / derived node separation with explicit provenance (`SourceRef` → `ContextNode`).
2. A durable, structured contradiction ledger, not ad hoc notes.
3. A human review/publish gate between any generated content and a committed static fixture.
4. A bounded, read-only, allowlist/blocklist-governed repo context pack, with no token/credential use.
5. Config-driven, search-first navigation for the graph console sidebar.
6. The "snapshot" metaphor for versioned static exports of graph state — as flat files, not a database.
7. A cinematic dark/neon visual language consistent with MellyCore's existing design system.

## 4. What MellyCore Avoids For Now

1. Any live database, ORM, or hosted backing store (Neon or otherwise).
2. Any file watcher, Obsidian plugin, or live-sync vault integration.
3. Any autonomous agent write-loop into the graph without human review.
4. Any GPL-licensed code, markup, or asset copying (explicitly: no gethomepage/homepage code).
5. Any GitHub token, PAT, or authenticated API call for context-pack generation.
6. Any specific visual claim about the TikTok references without attached evidence.
7. Any runtime/backend/API implementation of any kind — this phase is docs-only.

## 5. Static-First Product Decision

The MellyCore Living Context Graph MVP will ship as **static Markdown/JSON fixtures plus a design specification** — no live database, no live API, no file watcher, no autonomous ingestion. A human-reviewed ingest workflow (`[[../../shared_context/SOURCE_INGEST_WORKFLOW]]`) produces versioned static fixtures that a future, separately approved frontend task may render read-only, consistent with MellyCore's existing static-first homepage posture (`[[../../docs/specs/MELLYCORE_HOMEPAGE_SPEC_001]]`).
